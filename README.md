# HTML資料コメントレイヤー — 索引

既存のHTML資料に、Figma風のレビューコメント機能を後付けする。サーバもビルドも不要で、
できあがるのは1個のHTMLファイルのまま。Slackやメールで渡せば、受け取った側はブラウザで
開いてコメントを書き、コメントごと埋め込まれたHTMLを書き出して返せる。

コメントの完了・完了取り消し（完了は削除せず一覧の最下部へ。「完了済み N件」の区切りを
押せばまとめて畳める）、返信スレッド、優先度
（必須 / 要望 / 軽微）、書いたあとの担当者の付け替え、更新順と優先度順の並び替え、全コメントをMarkdownで書き出す
「AIに渡す指摘をコピー」（AI修正指示にそのまま貼れる）、未保存コメントのlocalStorageへの
自動退避・復元も備える。イラスト付きの使い方ガイド（画面左下の「使い方」で開く。自動表示はしない）
が資料に同梱されるので、受け取った人は説明なしで書き込みを始められる。
複数人が別々に書いて返してきたファイルは `--merge` で1つに合流できる。
一覧はマウスだけでなく `Tab` と `Enter` でも辿れる。

AIに直させたあとは、AIが出す `review-state.json` を `--apply-state` で流し込めば、
**どの指摘が対応済みかを資料に書き戻せる**（v2.14）。書き戻された完了は「AIの自己申告」なので、
引用文が本文から変わったかを機械で照合し、確かめられなかったものは「未検算」として残す。
人が「確認済みにする」を押すまで消えない。ファイルの往復で分岐した版は `comment-meta` に
系譜として残り、`--merge` が「別の資料」「親子」「分岐」を見分ける。

UIは**デジタル庁デザインシステム（DADS）**に準拠し、絵文字は使わず 24×24 のインラインSVG
アイコンで統一している。詳しくは `SKILL.md` の「見た目の決まり」を参照。

## 構成

- `SKILL.md` — ワークフロー本体（使い方・落とし穴・検証手順）
- `CHANGELOG.md` — 変更履歴（何をなぜ変えたか。設計判断の理由はここと `SKILL.md` に集約する）
- `assets/` — 資料に差し込む本体
  - `comment-layer.html` … CSS・マークアップ・スクリプトを1つにまとめたドロップイン・ブロック
- `scripts/` — 実行スクリプト
  - `add_comment_layer.py` … 資料への追加／更新／除去／合流／AI完了の書き戻し
  - `verify.mjs` … ヘッドレスChromeでの動作確認
  - `verify_cli.py` … `add_comment_layer.py` 側の動作確認（Chrome不要）
  - `cdp.mjs` … `verify.mjs` が使うChrome操作ドライバ（依存ゼロ）

## 最短の使い方

```bash
python3 scripts/add_comment_layer.py 資料.html      # → 資料_commented.html
node    scripts/verify.mjs 資料_commented.html      # → 全項目 passed になればOK

# 2人ぶんのレビューが返ってきたら
python3 scripts/add_comment_layer.py Aさん_commented.html --merge Bさん_commented.html

# AIに直させたあと、対応済みの指摘を資料に書き戻す
python3 scripts/add_comment_layer.py 資料_commented.html --apply-state review-state.json --in-place

# いまの状態を見るだけ（版・系譜・コメントの内訳。書き込む指定とは併用できない）
python3 scripts/add_comment_layer.py 資料_commented.html --check
```

## 資料側に必要な条件

1. ページ本体が普通にスクロールすること（`body{overflow:hidden}` ＋ 内側divスクロールにしない）
2. ピンの基準にしたい要素があれば `data-comment-host` を付ける（無ければ自動選択）

条件を満たしているかは `--check` が教える。詳細と理由は `SKILL.md` の「落とし穴」を参照。

## 依存

- `add_comment_layer.py` … Python 3（標準ライブラリのみ）
- `verify.mjs` … Node 22+ ／ ローカルのChrome・Chromium。
  既定の場所以外に入れている場合は `CHROME_PATH` で指定する。

## このレイヤー自身を直すとき

本体は `assets/comment-layer.html` の1ファイルに全部入っている（CSS・マークアップ・スクリプト）。

```bash
# 1) assets/comment-layer.html を直す
# 2) サンプルに流し込む（これを忘れると古いレイヤーを検査してしまう）
python3 scripts/add_comment_layer.py ../../サンプル/demo-要件レビュー_commented.html --in-place
python3 scripts/add_comment_layer.py ../../サンプル/楽天サンプル_commented.html   --in-place
python3 scripts/add_comment_layer.py ../../サンプル/demo-要件レビュー_確認用.html  --in-place
rm -f ../../サンプル/*.bak

# 3) 検証（v2.14.0 から3本。ブラウザ側2本＋CLI側1本）
node    scripts/verify.mjs    ../../サンプル/demo-要件レビュー_commented.html  # 60〜90秒
node    scripts/verify.mjs    ../../サンプル/楽天サンプル_commented.html       # 60〜90秒
python3 scripts/verify_cli.py ../../サンプル/demo-要件レビュー_確認用.html     # 数秒
```

**★資料の割り当てを間違えないこと。**

| スクリプト | 渡す資料 | 理由 |
|---|---|---|
| `verify.mjs` | `demo-要件レビュー_commented.html` と `楽天サンプル_commented.html` の**2本だけ** | 検査対象はレイヤーの挙動。コメントは各テストが自分で作る |
| `verify_cli.py` | `demo-要件レビュー_確認用.html` | **コメントが入っている資料が必要**（`_commented` の2本は0件なので `--apply-state` を試せない） |

`_確認用.html` を `verify.mjs` に渡すと4件落ちるが、これは **v2.13.0 でも同じ既存問題**で
回帰ではない。落ちたら「資料を間違えた」と思うこと。

- **`verify.mjs` は必ず2本とも流す。** demo資料は `*{box-sizing:border-box}` を敷いており、
  楽天サンプルは敷いていない。**1種類でしか見ないと寸法の不具合を取り逃す**（v2.9.0 で実際に踏んだ）。
- 先頭・末尾のバージョン記述と `var VERSION` の**3箇所**を必ず揃える。
- ページ遷移は `b.goto()` ではなく `verify.mjs` の `goto()` ラッパーを使う
  （レイヤーの起動を待たずに評価すると `host` が null のまま踏む）。
- **ページを開き直したら `PAGE_HELPERS` を入れ直す**（`window.__vt` は遷移で消える）。
- ★**「1回だけ落ちて再実行で通る」は v2.14.1 で原因を特定して直した。**
  書き出したファイルに `data-cl-host` が焼き込まれており、起動前から印だけが在るせいで
  起動待ちが素通りしていた。症状は当たりどころ次第で `createTreeWalker … not of type 'Node'`
  （host が null）と `parentNode`（pinBox が null）の2つに割れる。**また出たら、まず
  「起動待ちが素通りしていないか」を疑う**（詳細は `CHANGELOG.md` の v2.14.1）。
- 変えた理由は `CHANGELOG.md` に、踏んだ穴は `SKILL.md`「落とし穴」に必ず残す。

### どこに何を書くか（★同じ話を2箇所に書かない）

3つあるものは必ずズレる。**役割で切って、1つの話は1箇所に置く。**

| 置き場所 | 担当 | 性質 |
|---|---|---|
| `CHANGELOG.md` | **決定と、採らなかった案** | 不変の履歴。あとから編集しない |
| `SKILL.md` | **いまの挙動** | 仕様。変更のたびに書き換わる |
| 使い方ガイド | **利用者に届く1文** | 読者は非開発者 |

`CHANGELOG` に「いまの挙動」を書くと、次にそこを触ったとき2箇所直すことになる
（v2.14.0 で「検算の限界」を3箇所に書いてしまった。次に触るときに揃えること）。

**項目数のような「いまの挙動ではない数字」も、このルールの対象。** 検証の項目数は
`CHANGELOG`（その版で何項目だったか＝履歴）にだけ置き、`SKILL.md` / `README.md` では
「全項目 passed になること」で見る。そうしないと1項目足すたびに4ファイル直すことになる。

**`SKILL.md` のフロントマターの `description` は、機能の説明を足す場所ではない。**
スキルがいつ呼ばれるかを決める設定なので、機能追加のたびに説明を継ぎ足すと
そのうち読まれない長さになる（v2.14 の時点で527文字）。**次に足すのはトリガー語だけ**にする。

### 今後の候補（未着手）

- **`op` を1枠で持つのをやめる。** 系譜の `op` は1つしか持てないため、`--carry-from --apply-state`
  や `--merge --apply-state` のような併用では、どちらを優先しても失われた方の情報は
  他から復元できない（`carry`/`merge` は系譜にしか痕跡が無い。`apply-state` は
  `resolvedBy:"AI"` に痕跡が残るが、人が「確認済みにする」を押すと上書きされて消える）。
  いまは `carry`/`merge` を優先。優先度は低く、**「その組み合わせを実運用で何回使うか」を
  数えてから判断する**（単独指定なら現行実装で完全に記録できている）。
  実装するときの形は `op` を表示用の主ラベルとして残し `ops: []` を足すのが良い
  （合成文字列にすると `OP_JA` の引きが外れる）。詳細は `CHANGELOG.md` の v2.14.1／v2.14.2。
- **ピンを「アンカー要素からの相対」で持つ。** v2.13 の比率（`yr`）で誤差は
  1793px → 70px まで落ちたが、原理的にはまだ近似。完全にしたいなら、刺した座標に
  いちばん近いブロック要素を掴んで、その要素からの相対で持つしかない。
  要素の特定は再アンカーと同じ問題（＝**曖昧なら貼らない**）になるので重い。
  ★v2.14 で**ピンのAI完了は構造的に検算できない**ことが分かったので、これを入れると
  検算の対象にできる。**以前より価値が上がっている。**
- **`--merge` の複数指定**（`--merge A --merge B`）。2ファイルずつ2回流せば同じ結果になるので、
  手間が減るだけ。優先度は低い。
- **一覧の絞り込み**（「必須だけ表示」など）。足すなら「件数は全件のまま出す」
  「開き直す取っ手が必ず残る」を守れる形でのみ（`SKILL.md`「落とし穴」参照）。
- **検証の分割。** `verify.mjs` は1本60〜90秒。分けるなら「レイヤー本体の検査」と
  「資料の性質に依存する検査」で切るのが素直（後者だけ2本の資料で回す）。いまはまだ必要ない。
- **`--repair`（壊れた `comment-store` の救出）。** v2.14 で書き戻し口を `--apply-state` に
  絞った時点でAIがJSONを触らなくなり、壊れる経路が実質なくなったので入れていない。
  残る経路は「人が手で埋め込みJSONを編集した」場合だけで、救える範囲も一様ではない
  （`COMMENT-LAYER` が生で入った＝可能／JSONとして不正＝不可／生の閉じ script タグ＝
  真の終端がヒューリスティックでしか決まらない）。**経路を塞ぐ側が本筋で、`--repair` は保険。**
  なお `--check` は JSON が壊れていても落ちずに所見を出すので、検出はできる。

### やらないと決めたもの

- **タッチ環境への対応。** スマホは考慮しない（どうせコメントが書けない）。
- **手で選んだ色の近似警告。** 自動割り当ては最遠色を選ぶが、色ピッカーで自分で選んだ場合は
  近くても警告しない。
- **下書きの保存ボタンのツールチップ化。** 入力中は視線がテキストエリアにあるので、
  ホバーしないと出ないツールチップでは気づけない。常時表示のままにする。
- **サイドバーのフォーカストラップ。** モーダルではないので閉じ込めてはいけない。
- **「完了を畳む」設定をファイルに焼くこと。** 並び順と同じく読み手の都合であって、
  資料の中身ではない。
- **カードで `Space` を奪うこと。** 「スペースでスクロールできること」が最優先の約束。
- **`--merge` でユーザーを名前で寄せること。** 同姓の別人が潰れる方が害が大きい
  （同名別IDは合流時に名指しで警告する）。
- **AIに返信・コメントを書かせること。** 本文を見れば何を直したかは分かる。9件の指摘の下に
  AIの作文が9件並ぶと人間の議論が薄まるし、社外レビュアーに「AIに処理された」印象を与える。
- **埋め込みJSONをAIに直接編集させること。** ファイル破壊の防止をプロンプト遵守に賭けない。
  書き戻し口を `--apply-state` に絞った結果、エスケープ規約をAIに課す必要がまるごと消えた。
- **Python 側で引用照合して未検算件数を出すこと。** 照合が2実装になり、JSを触るたびにズレる。
  失敗の向きが「黙って安心させる」方なので、`--check` は「不明」と言うのが正しい。
- **「確認済み」を新しいフィールドで持つこと。** 既存の `resolved` を流用して `resolvedBy` を
  人に付け替える方式にした（スキーマ不変を優先）。副作用として**AIが完了にした時刻は失われる**が、
  合意のうえ。
